# GrantOnce 分匣授權

已登記服務先說需要什麼，你確認之後才做法源檢查；你簽署後，資料來源才直接交付辦理機關。

GrantOnce 的語言模型 Agent 負責理解問題、找到已登記服務與協調流程，不替使用者授權，也不接收資格資料值。服務機關回傳本次必要需求，委託人確認後系統才做目的與法源檢查，通過了才鑄出匣讓他用 passkey 簽；資料來源機關驗證簽章、請求機關持有證明與法定目的，再把**述詞**（是／否、級距）直接交付請求機關。任一條件不成立就 fail closed。

這是黑客松演示，不是正式政府系統。所有個資都是合成的。

## 怎麼跑

```bash
npm install
npm run dev            # http://localhost:43127

npm run test:flow      # 授權層與巡檢檢查
npm run test:mcp       # MCP 檢查
npm run test:race      # 跨 process 檢查（會開子行程）
npm run test:all       # 以上三個
npm run test:rehearsal # 77 項，逐句對照演示腳本，需先開 dev
npm run test:mutate    # 29 個注入的 bug，每個都必須被上面某個測試抓到
```

需要 Node 20+。沒有環境變數、沒有資料庫、沒有真實 MyData。

⚠️ **請用 `localhost`，不要用 `127.0.0.1`。** WebAuthn 不接受 IP 位址當 RP ID，在 `127.0.0.1` 上按 passkey 會直接失敗。畫面會擋下按鈕並說明，但省得你在台上才發現。

## 這個演示在回答什麼

主辦方對「跨部門資料互通」的說法是：**根源是法規而非技術**。公務機關只能在「執行法定職務必要範圍」內蒐集處理個資（個資法 §15／§16），且不得逾越特定目的必要範圍（§5）。沒有合法事由就只能走公文。

所以這裡沒有繞過法規，而是**把法規編碼成兌現時會被檢查的條件**：

| 法規 | 在程式裡是什麼 |
| --- | --- |
| §15 第 1 款　執行法定職務必要範圍內蒐集處理 | 目的登記表。內建三筆在 `lib/purposes.ts`；服務機關在前端「登記台」掛上或下架，寫入 store。每個目的寫死允許的述詞集合、請求機關、告知事項與法源。 |
| §16 本文　於執行法定職務必要範圍內利用 | 兌現時比對匣的述詞是否在該目的的上限內 |
| §5　不得逾越特定目的之必要範圍 | 述詞取代原始欄位。育兒津貼一個原始欄位都不需要 |
| §6 第 1 項　特種個資 | 健保欄位永不授權 |

條號都對過[全國法規資料庫](https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=I0050021)。
補助本身的作用法只在查證過的情況下才引：育兒津貼引兒少權法 §23 第 1 項第 3 款與第 2 項；
冷氣汰換補助**不引**，因為它實務上依特別預算與行政辦法辦理，沒有查到明確的法律授權條文。

主辦方那句「重點不是你有沒有憑證，而是**驗證方有沒有權力驗證**」，就是第二把鑰匙。

## 端到端流程

```text
1 服務探索       使用者詢問，找出已登記服務
2 服務需求確認   服務回傳本次必要資料，使用者決定要不要往下走
3 登記與法源檢查 確認之後才檢查：目的在登記表內、個資依據成立
4 最小化         通過檢查才鑄出授權匣，匣裡只有述詞
5 使用者簽署     閱讀告知事項後以 passkey 簽章
6 機關對機關交換 來源驗證簽章與持有證明，直接交付請求機關
7 服務處理       請求機關以述詞辦理案件
8 回覆與稽核     結果回覆使用者，每一步都留在稽核軌跡
```

第 2 步與第 3 步刻意分開。需求被確認之前，state 裡不存在任何可簽署的匣——先問「這個人要不要辦」，才問「這個機關有沒有權力要」。反過來做，等於在替一個沒人開口要的服務先鑄好授權。

公開搜尋只負責發現可能存在的服務。未完成目的、法源、請求機關、必要述詞與來源轉接器登記的結果，不能建立 Grant。使用者簽章也不是萬用法源：即使簽了，超出法定職務或目的必要範圍的請求仍會被擋下。

## 兩把鑰匙

**第一把 · 委託人簽章**
匣是一段 JSON，用 ed25519 簽過。簽章涵蓋 `requestId`、請求機關、資料來源、直接交付設定、結構化個資告知事項、`aud`、`cnf.jkt`、`jti`、`exp`、述詞清單，以及同意畫面上實際顯示的文字。兌現前會重新序列化 body 與簽署內容逐位元比對，並再次和服務登記內容比對。

**第二把 · 機關法定職務**
機關必須簽出持有證明，證明自己握有 `cnf.jkt` 指向的金鑰，而且那份證明綁定這張匣的摘要（匣編號會重複使用，只綁編號會被重放）。同時目的登記表要確認這些述詞在該機關的法定職務內。

**缺一不可。** 委託人被釣魚簽了所得欄位，照樣被目的登記表擋掉——因為社會局辦育兒津貼沒有蒐集所得的法定依據。

## 最小揭露

育兒津貼實際需要的是四件事，不是一份謄本：

| 機關收到 | 值 |
| --- | --- |
| 是否設籍新北市 | `true` |
| 是否一年內遷入 | `true` |
| 是否為法定親子關係 | `true` |
| 幼兒年齡帶 | `0-2` |

滿 2 歲後改適用的托育補助（G-丙）只要三件事：設籍、親子關係、年齡帶——連「一年內遷入」都不需要。

姓名、地址、戶號、出生日期**都沒有離開金庫**。冷氣補助同理：給的是用電級距與一個對經濟部專屬的帳戶假名，不是電號、不是逐月度數。

**成對假名**：甲與乙拿到的識別碼不同，兩個機關就算私下交換資料庫也拼不回同一個人。假名是 HMAC 而不是純雜湊——身分識別碼的空間小到可以窮舉，無金鑰的雜湊等於沒有保護。

## 憑證重用：出生證明那 3–5 天只付一次

主辦方的案例二是出生證明要調 3–5 個工作天，而很多申辦都要它證明親子關係。

戶政從金庫派生「是否為法定親子關係」並簽發一張效期一年的憑證，存進皮夾。之後每次申請都出示同一張，不再調閱。金庫只在**發證**那一刻被讀取。機關會獨立驗發證機構的簽章，而且驗的是簽章涵蓋的值本身，不是旁邊那個可以被改掉的欄位。

這就是「把 MyData 與數位憑證串起來」：MyData 是取得資料的管道，皮夾是出示資料的方式。

## 撤銷：分成三件事，誠實回答

| 撤銷什麼 | 怎麼做到的 |
| --- | --- |
| 停止 Agent 協調委託 | ✅ 即時。停用後流程不再接受新的 Grant 簽署，未兌現的一併作廢 |
| 撤銷還沒兌現的匣 | ✅ 短效（600 秒）＋ 一次性 `jti` 清單，兌現端擋下 |
| 撤銷已交付給機關的述詞 | ❌ **收不回來** |

第三項收不回來，所以唯一的防線是一開始就少給。育兒津貼那四個述詞就算收不回來也無所謂——它本來就不含個資。

## 高風險攔截

攔截發生在**提案階段**，委託人根本不會看到可以按的同意按鈕：

- 逾越該目的法定職務範圍 → 攔截
- 索取的機關不是該目的的主管機關 → 攔截
- 不得授權的欄位 → 攔截，無論委託人是否同意。兩者理由不同，訊息也分開講：
  健保是**個資法 §6 第 1 項**法律禁止；所得**不是** §6 特種個資，是本設計依 **§5 比例原則**自行排除
- 超過委託設定的敏感度上限 → 攔截
- 含原始個資、或一分鐘內重複兌現同一目的 → 升為「需額外確認」，簽署按鈕要先勾選確認才會啟用

## 動態授權與主動推送

幼兒滿 2 歲後改適用不同補助。金庫欄位面板下方可以把時間往前推，代理人會主動推送資格變更並重新比對——**原本簽過的匣不會自動沿用**，條件變了就要重新簽一張新的（新的 `jti`、新的效期、新的簽章）。

推送不是「有人來讀的時候才算」。`lib/agent.ts` 的 `runAgentTick()` 是一次巡檢，MCP server 每 `GRANTONCE_TICK_MS`（預設 15 秒）跑一次，沒有任何人呼叫工具也會跑：開著 `npm run mcp` 什麼都不做，`get_notifications` 自己會長出東西。標題列的「代理人上次巡檢」讀的就是這一輪留下的時間戳。

偵測器有九條，全部寫在 `lib/rules.ts` 的 `scanForChanges`，是純函式——不讀金庫、不呼叫模型：

| 推播 | 什麼時候 |
| --- | --- |
| 育兒津貼資格已改變 | 幼兒滿 24 個月 |
| 再 N 個月條件會變 | 距 24 個月 ≤ 3 個月 |
| **你現在符合某個補助** | 規則引擎比對出還沒有匣的方案 |
| 憑證已到期／即將到期 | 已過期／距到期 ≤ 7 天 |
| 匣即將逾效期 | 已簽未兌現，距 `exp` ≤ 120 秒 |
| 委託即將到期 | 距 `validUntil` ≤ 7 天 |
| 上一次請求被擋下 | 收件匣有拒絕紀錄 |
| 匣還在等你簽 | 提案超過 60 秒未簽 |

第三條是重點：時鐘前進 13 個月時，代理人**同時**說「育兒津貼不再成立」和「你現在符合未滿 5 歲幼兒托育補助（G-丙），要不要我幫你辦」。主動推送不是只會報壞消息。

每則推播有一個穩定的 `key`，去重就靠它——改標題不會重複推播，而 `key` 裡帶 `jti`，所以換了一張新的匣就會推出屬於它自己的那一則（匣編號會跨提案重複使用）。連跑十次巡檢，推播數量不變；`staleAfter` 過期的未簽收推播會被自動清掉。

## 推播給人看的，和推播給模型看的，是兩段文字

每則推播寫兩份：

- `body` 給委託人，**可以**帶述詞的值（「離開 0-2 年齡帶」）——那本來就是關於他的事實。
- `summaryForAgent` 給模型，**不含任何值**（「已離開育兒津貼的適用範圍」）。

`get_audit` 一直宣稱「不含述詞的值」。推播是同一份程式寫給同一個讀者的，所以那句話在這裡也要成立：`mcp/tools.ts` 的 `claimValueLeakIn()` 會拿皮夾裡實際持有的述詞值去掃每一份要回給模型的 payload，`get_notifications`／`get_pending_actions`／`get_audit` 三個工具回傳前都跑一次。

一個誠實的邊界：`true`／`false` 這種值和 JSON 裡任何一個布林值長得一模一樣，用字串比對抓不出來，所以它們不在掃描名單裡。這正是 `summaryForAgent` 一開始就寫成不提任何值、而不是指望這道檢查去攔的原因。

## 簽章金鑰：passkey 的 PRF

passkey 不直接簽匣。WebAuthn 只能簽一段不透明的 challenge，而且它的系統彈窗**無法顯示你在簽什麼**。

所以走 PRF 擴充：認證器在通過 Face ID／指紋後回傳一段確定性秘密，用它派生一把 ed25519 金鑰，簽的是人看得懂的匣本身。私鑰不儲存，每次簽都重新派生、用完即丟；伺服器只有公鑰。

**盲簽的緩解**：把同意畫面上實際顯示的那段文字一併納入簽章範圍，事後爭議時證明得了「委託人當時看到的就是這段」。畫面上的「看我簽的是什麼」就是在展示這件事，展開後可以看到待簽的原始 bytes。

私鑰只存在註冊當下那個瀏覽器來源。換網址、換裝置或清過資料，畫面會說「這個瀏覽器沒有這把金鑰」並讓你重新註冊，而不是等到簽署失敗。認證器不支援 PRF 時可改用軟體金鑰，流程一樣，安全性較弱，畫面會標示。

## 模型只當「聽懂」那一層（選用）

預設沒有模型：意圖比對是 `lib/agent/turn.ts` 裡的六條正則。要讓它聽得懂更多說法，
在 `.env.local` 填一個 OpenAI 相容的 router（clawrouter 等）：

```
AGENT_MODEL_BASE_URL=https://your-router.example/v1
AGENT_MODEL_API_KEY=...
AGENT_MODEL=claude-opus-5
```

模型先從 `lib/agent/skills/` 選擇適用的 local skill，再把自由文字對應到六個
粗粒度意圖之一，外加「有沒有提到搬家」。第一個 skill 是 `apply-with-grant`：它把
補助對話分成「說明／釐清／開始比對」，只有「開始比對」能進入規則引擎並提出 Grant。
Skill 是對話 playbook，不是權限來源。
**它看不到金庫、不挑述詞、也不決定誰有資格**——那些仍然由規則引擎與目的登記表
決定。`lib/agent/intent.ts` 的回傳型別就是那條界線：一旦它變寬到能影響「要求哪些
述詞」，「規則引擎決定授權」這個主張就不成立了。

沒有 key、逾時、回覆解析不了、標籤不在列舉裡——任何一種都退回正則，
**demo 的每一步照常運作**。實測把 router 指向不存在的位址，`/api/chat` 仍在
0.07 秒內正常回應。

刻意不用 JSON-schema `response_format`：OpenAI 相容的 router 對多數上游模型會
拒絕它。要一行 JSON 再自己嚴格驗證，簡單而且真的跨得過去。

## 模型不能簽

MCP 工具清單裡沒有任何簽署工具，而且 `mcp/test.ts` 不是用名字判斷——它把每個工具都從乾淨狀態呼叫一次、餵進一份會被接受的簽章，然後要求沒有任何匣變成已簽署。模型也拿不到金庫值：每個工具回傳前都跑一次外洩檢查。

## 文件中心

啟動 Web 後開啟 [`http://localhost:43127/docs`](http://localhost:43127/docs)。文件依一般使用者、
開發者串接、政府導入與安全參考分類，支援關鍵字搜尋、可分享的文章 URL，以及只讀的
文件代理人。代理人只檢索 `lib/docs.ts` 的內容，不會讀 demo state，也不會呼叫任何授權工具。

## 什麼是假的

- 林曉晴、子女、地址、戶號、所得、健保、電表、用電量：全部合成
- MyData 金庫：本地 JSON
- 機關與發證機構的金鑰由固定種子派生，方便 demo 重啟後身分不變
- 送件：只改狀態，不會送到任何機關
- 請求機關、資料來源機關與兩者間的直接交付：由同一個伺服器程序模擬，尚未形成真實跨機關信任邊界
- 申辦進度（`applicationStatus`）：`submitted` 之後的每一格都由 `POST /api/agency/advance` 手動推進。這是 fixture，讓「進度追蹤」在協定裡有位置，不是假裝真的接上了機關

## 什麼是真的

- ed25519 簽章與驗簽，且**驗過的位元組就是被授權的物件**：兌現前比對 `serializeBody(body) === serialized`，憑證交付前比對值與簽章內容
- 受眾綁定與金鑰持有證明：匣**不是** bearer token，撿到也沒用
- 機關持有證明綁定這張匣的摘要並有 120 秒時效，舊證明不能重放到新匣
- 一次性 `jti` 清單，跨 process 用檔案鎖保護讀改寫，六個行程同時兌現只會有一個成功
- 目的登記表獨立於委託人同意之外執行
- 服務需求、請求機關、資料來源、直接交付方式與個資告知事項都納入簽章並在兌現時重新比對
- 成對假名用 HMAC，跨機關無法比對
- 上一版 schema 的 store 檔會被隔離而不是讓整個 app 崩掉

## MCP（協定客戶端）

MCP 是 GrantOnce 的非信任客戶端：可規劃、兌現、攔截、稽核，**不能簽署**。可貼進 Grok Bot／Cursor 的協定說明：[`docs/grok-bot.md`](docs/grok-bot.md)。專案已帶 `.cursor/mcp.json`（stdio）。

參考實作裡的補助申請是 conformance profile，不是協定範圍。

```bash
npm run mcp
```

與錢包 UI 共用 store（預設 `/tmp/grantonce-runtime.json`）。寫入互斥上鎖，讀取偵測檔案異動。

工具：`search_purposes`、`plan_applications`、`get_grant_for_signature`、`redeem_grant`、`request_claims`、`submit_application`、`revoke_grant`、`stop_delegation`、`get_audit`、`get_notifications`、`acknowledge_notification`、`get_pending_actions`。

`search_purposes` 會做公開搜尋（維基、`*.gov.tw` 連結），並另外標出本 runtime **目前能 mint Grant** 的子集。目的登記表不是全世界；搜到補助 ≠ 授權。`plan_applications` 只有登記表＋資格成立才提案，不能發明述詞。宿主若已有網搜，應先搜，不要被少數幾筆可發票目的綁死。MCP **沒有**寫入登記表的工具——掛上／下架是人類在前端「登記台」做的。

## 登記台

頂欄膠囊「授權 | 金庫 | 機關 | 登記台」。服務／請求機關在登記台掛目的、改允許述詞與告知事項、下架。發證端已上線的述詞才能勾；不能發明 `disaster.*` 這類還沒 adapter 的欄位。

寫入走既有的 `POST /api/state`：


## 推播與待辦的三個工具

- `get_notifications` 先跑一次巡檢再回傳，所以只會輪詢的 client 也一定拿到新鮮狀態；可以帶 `unacknowledgedOnly` 與 `since`。
- `acknowledge_notification` 簽收一則推播並記一筆稽核。簽收只表示看過了，不會授權任何事。
- `get_pending_actions` 是衍生值、不落地：現在卡住的每一件事、卡在哪一方（委託人／機關／發證機構／代理人），以及下一步該呼叫哪個工具。**建議的下一步永遠不可能是一個造成授權的動作，因為那種工具不存在**——`mcp/test.ts` 會把每個被建議的工具實際跑一遍，餵進一份會被接受的簽章，然後要求沒有任何匣變成已簽署。
- `get_audit` 可以帶 `since`（稽核編號或 ISO 時間）只取增量，並回傳 `cursor` 讓長跑的 agent 下次直接續讀。`since` 不合法時退回全量並在 `note` 說明，不丟錯。

除了工具，server 還宣告了 `logging` 與 `resources`（`subscribe` + `listChanged`）兩個能力：巡檢推出新東西時會送一則 logging notification，以及對資源 `grantonce://notifications` 送一次 updated。訂閱與取消訂閱是自己接的 handler——宣告了 `subscribe: true` 就要真的答得出 `resources/subscribe`。Client 不支援時安靜降級，輪詢 `get_notifications` 照樣可用。

## 這個設計的名字

- **UMA 2.0 / OAuth RAR（RFC 9396）**：結構化的授權請求，不是 scope 字串
- **RFC 8705 / 9449 的持有證明**：`cnf` 綁定讓匣不再是 bearer
- **W3C VC 的 issuer–holder–verifier**：發證機構、皮夾、機關
- **TW FidO／行動自然人憑證**：正式版的簽章來源，demo 用 passkey 代替

## 已知邊界

- **請求與來源機關在部署層尚未分離。** `/api/grants/redeem` 與 MCP 的 `redeem_grant` 在同一個伺服器內模擬請求機關持有證明、來源驗證與直接交付。授權層有偽造、跨機關與服務需求竄改測試，但正式版必須把雙方私鑰與來源轉接器移到各自系統，並用 mTLS 或 GCA 機關憑證認證與點對點傳輸。
- **資料交付給機關之後，技術上管不到。** 這裡的答案是最小揭露與稽核，不是宣稱做得到。
- **沒有任何 API 有身分驗證，狀態也只有一份。** 單人演示沒問題；多人同時開會互相影響。
- **走「直連」模式**：兌現端知道委託人在申請什麼。錢包模式（機關不回報兌現）隱私更好但撤銷更難，未實作。
- **passkey 的 PRF 路徑需要真實認證器**。自動化測試只覆蓋到來源規則與軟體金鑰路徑；上台前請在該台機器上實際按一次。
